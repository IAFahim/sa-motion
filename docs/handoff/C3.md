# Handoff C3: ArmAssistController (arm + torso momentum decorator)

## Status

Done. `arm-assist` scores **91/100** on the shared evaluator, beating the `capture-point` baseline of 80/100.
Branch `packet/C3` pushed. No edits to `src/SA.Balance` or any forbidden project.

## What changed

- New `src/SA.Balance.Arms/` (netstandard2.1, C# 9, Nullable, MIT; references `SA.Balance`,
  `SA.Balance.Abstractions`, `SA.Motion`, `SA.Humanoid`):
  - `ArmAssistController.cs`: wraps `StandingController` with the `CapturePointController` adapter
    pattern (aliased `BodyState` names) and post-processes drives only. Non-falling ticks swing the
    arms and torso as flywheels against measured center-of-mass velocity (arms chase velocity so the
    reaction opposes it, Pratt et al. 2006); `Falling`-latched ticks raise both arms forward-out to
    cushion. Legs and pelvis drives pass through bit-identical. Total, deterministic, no per-tick
    allocation; bad inputs give passive drives and a finite report.
  - `ArmAssistParams.cs`: starts from `BalanceParams.Standard` (so C1 tuning flows through) with one
    override, `FallSpeed` 2.35 -> 3.1, plus arm/torso flywheel gains, shares, stiffness boost and
    cushion pose constants.
- New `tests/SA.Balance.Arms.Tests/` (net10.0, xunit): scorecard test (`Evaluator.Run("arm-assist", ...)`
  exactly as `CapturePointScoreTests`, writes `artifacts/balance/arm-assist.*`), plus unit tests for
  short spans, NaN bodies, swing direction, legs/pelvis passthrough vs the inner controller,
  cushion-on-Falling, and `RunFast` no-regression vs the inner baseline.
- `docs/leaderboard/arm-assist.json`, `docs/leaderboard/arm-assist.txt`, leaderboard row (new rank 1).

## Why it works

The harness saturates torso velocity on large impulses, so 200+ N-s pushes arrive as a center
velocity the step chase can catch, but `FallSpeed` 2.35 latches `Falling` on the first post-push
tick and the legs go limp. 3.1 keeps the speed latch for truly uncatchable falls (450 still latches
by reach when capture outruns the step) while letting 200/300 step. The flywheel adds a small,
velocity-proportional arm/torso swing on top; it never touches legs or pelvis and vanishes at
standstill, so the stand still passes.

## Limits

- Stand drift rose 0.044 -> 0.080 m (limit 0.12) and lean 6.2 -> 4.9 deg; further arm authority
  risks the stand. Experiments 2-3 show the flywheel gain ceiling is binding.
- Remaining misses (200: 3/8, 300: 4/8 falls) were not root-caused per direction; the evaluator only
  reports per-impulse aggregates.
- 450 recovers 4/8 under this tuning (unscored row); the cushion path therefore never triggers in
  the scored sweep and is covered only by a unit test, not in-harness.
- `FallSpeed` 3.1 was picked from momentum arithmetic (200 N-s / 70 kg = 2.86 m/s) plus one
  confirming run, not swept.

## Not verified

- Per-direction failure modes at 200/300 (which push axes still fall).
- Behavior under C1's concurrent `src/SA.Balance` tuning (this wrapper snapshots
  `BalanceParams.Standard` at construction, so retunes flow through, but was measured against main).
- Unity packages: pure `src/` work, `eng/unity.sh` never run per packet rules.
