# Handoff C19: shape systems as jobs, compact palette staging, a player proof, Windows fake tools

Continues `docs/handoff/C17.md`. C17 and C18 moved `SharedFamilySystem` and `SharedFamilyPaletteSystem` in com.sa.unity to Burst jobs. This round did the same for the two Shape systems, fixed two things in the earlier work, and proved all four systems in a built Windows player.

Machine for every number: AMD Ryzen 5 8500G, NVIDIA GeForce RTX 3060, Windows 11 Pro, Unity 7000.0.0a16, Direct3D 12, 11 worker threads.

Things worth knowing before touching this code:

- **`IJobEntity` does not compile in `SA.Shape.Unity`.** The Entities source generator writes `Unity.Entities` without `global::`. Inside a namespace whose last part is `Unity`, that name resolves to the namespace itself, for the job and for the system that schedules it. The Shape jobs are `IJobChunk` for that reason.
- **Same output is recorded, not argued.** `ShapeJobTests` plays 40 steps on three shaped rigs (7 bones, 56 bones with two channels and morphs, 7 bones held live-physical): shape requests, an interrupt, a weight change, a seek, a pause, a 0.3 s frame, and an edit refused while live-physical. The recording was taken from the 0.3.7 systems at commit `ea7f447`, before they changed. The job versions match all 61,240 pose, channel, revision, deformation, morph and contact values and all 20,992 palette values read back from the GPU, bit for bit.
- **A zero-length frame after a normal one reports `TickConflict` once and leaves the pose alone.** That is 0.3.7 behaviour (`TimelinePose.Prepare` compares the frame inputs when the tick repeats). The recordings include it. It is not new.
- **Shaped rigs share the clip and table blobs** that `SharedFamilySystem` builds, through `SharedFamilySystem.ResolveLayouts`. A clip used by shaped and unshaped characters is parsed once.

Measured, `ShapeJobTests.CostOfTheShapeSystemsPerRig`, 300 shaped rigs of 56 bones with one skin each, median of 60 frames, four Editor runs per row:

| System | 0.3.7, main thread | Job |
|---|---:|---:|
| `ShapeTimelineSystem` | 16.5 to 22.1 ms | 1.7 to 2.1 ms |
| `ShapeSkinPaletteSystem` | 4.8 to 7.0 ms | 1.2 to 1.7 ms |

A run started right after a recompile reads about twice as high, because Burst is still compiling in the background. Those runs are left out.

## Two fixes to the earlier work

1. **The palette staging was as large as the whole GPU buffer.** The C18 version of `SharedFamilyPaletteSystem` kept a CPU copy indexed like the skin-matrix buffer. Next to a large GPU crowd that is tens of megabytes holding nothing. Both palette systems now measure first, then stage only the palettes they upload. Cost is unchanged within run-to-run spread (2.3 to 3.1 ms per frame for 1000 skins, against 2.7 to 3.1 ms before).
2. **The trace recorders could overwrite the fixtures.** They are explicit tests, and the documented command for SA.Tests passes `--include_explicit true`. On such a run the recorder ran before the comparison and rewrote the fixture, so the comparison could never fail. Recorders now write to `Library/SA.Recorded` in the project and say whether the result equals the fixture. With explicit tests included: 133 total, 130 passed, 0 failed, 3 skipped for missing assets, and all four recordings identical to the fixtures.

## Player proof

`Samples~/PlayerProof` in com.sa.unity plus the menu item **Tools > SA > Tests > Run Player Proof** (`Tests/Editor/PlayerProof.cs`; from a shell, `-executeMethod SA.Tests.PlayerProof.RunFromCommandLine`). It is a menu item and not a test, because SA.Tests is run with explicit tests included and a player build takes minutes.

The Editor serializes the four test worlds with `SerializeUtility.SerializeWorld`, copies the four recordings next to them in `Assets/StreamingAssets/SA.PlayerProof`, builds a player for the current platform and scripting backend into `Builds/SA.PlayerProof/`, runs it with `-saPlayerProof <report>`, and removes the StreamingAssets folder. In the player the probe loads each world, steps the systems through the same scene the tests play, compares every value with the recording, and reads the `Native` flag the jobs set through a `BurstDiscard` probe.

| Player | Scene | Values | Exact | Rigs on Burst |
|---|---|---:|---:|---:|
| Windows x64, CoreCLR | shared-family poses | 20,700 | 20,700 | 3 of 3 |
| | shared-family palettes | 17,248 | 17,248 | 2 of 2 |
| | shape poses and state | 61,240 | 61,240 | 3 of 3 |
| | shape palettes | 20,992 | 20,992 | 3 of 3 |
| Windows x64, IL2CPP | the same four scenes | 120,180 | 120,180 | all |

Both are release builds on Direct3D 12 with the RTX 3060. The first CoreCLR build took 17 minutes (shader variants), the IL2CPP build 39 minutes. `StreamBinaryReader` and `StreamBinaryWriter` are internal in this Entities version; the proof uses `MemoryBinaryWriter` and `MemoryBinaryReader`. Unity refuses to build a player into `Library`.

## Not verified

- Unity on Linux and macOS for any of this. The .NET suites ran on GitHub's Linux runner for sa-motion and on Linux and Windows for sa-inbetween, and passed.
- A real Generate with the NVIDIA model on Windows. It asks a licence question that is the owner's to accept.
- Real characters. Every scene here is synthetic (7 and 56 bone rigs built in test code). Tests that need the Synty or Mixamo assets are still skipped on this machine.
- The four bridge DLLs were rebuilt on Windows; their bytes differ from a Linux build of the same source.
- Unity 7000.0.0a12. `SharedFamilySystem` and `ShapeTimelineSystem` carry `Unity.Scripting.LifecycleManagement.AutoStaticsCleanup`, which 7000.0.0a16 asks for; whether a12 has that attribute was not checked.

## Left on purpose

- **Unity 7 statics warnings (UAL0010, UAL0013)** in files this work did not otherwise touch (the editor tools in com.sa.unity and sa-inbetween). Silencing one means choosing, per type, whether its static state should reset on a code reload. For `RecipeRunner` and its neighbours that choice changes what a designer sees after a reload, so it is the owner's.
- **Shared-family clips on the GPU engine** (plan packet C16). The CPU path now costs about 5.5 ms per 1000 characters, which is the measured bottleneck that packet asks for, but it is a packet of its own.
- **The 50,000-character GPU target.** `Documentation~/benchmark.md` in com.sa.unity has the phase timings: upload and dispatch, then fill, then layout.
