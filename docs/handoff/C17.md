# Handoff C17: flat clip storage and a span-only sampler

## Why

`docs/shared-family-contract.md` says: publish the validated track, block, segment and root data into immutable native storage, pass borrowed spans into the hot kernels, and never put the managed `SharedClip` into an ECS component or job. `SharedFamilySystem` in com.sa.unity 0.3.7 does not do that yet. It keeps `SharedClip` objects in a managed dictionary and samples every rig on the main thread, because the only sampling entry point was the instance method `SharedClip.Sample`, whose segments are jagged managed arrays (`LoadedSegment[]`, each with its own `byte[]` and `TrackBlock[]`).

This packet adds the missing portable piece, so a Burst job can sample a shared clip from a blob. It changes no existing code.

## What was added

| File | Contents |
|---|---|
| `src/SA.Animation/Streaming/SegmentSampling.cs` | `SegmentRange` (first sample, sample count, byte offset, byte length) and `SegmentSampling.Sample`, which takes only spans and scalars |
| `src/SA.Animation.Content/SharedClipStorage.cs` | `Measure` (block and byte counts) and `Write` (flattens a loaded `SharedClip` into caller-owned spans) |
| `tests/SA.Animation.Tests/SegmentSamplingTests.cs` | 12 tests |

Layout written by `SharedClipStorage.Write`:

- `segments[i]`: one `SegmentRange` per segment, in order.
- `blocks[i * tracks + t]`: the `TrackBlock` of track `t` in segment `i`. `TrackBlock.Offset` stays relative to its own segment's bytes.
- `bytes`: the segment payloads back to back; `SegmentRange.ByteOffset` and `ByteLength` locate each one.

`TrackDescription[]`, `RigidPose[] Root`, the additive reference and the contact weights are already flat arrays on `SharedClip` and copy as they are.

`SegmentSampling.Sample` runs `SampleLocator.Locate`, bounds-checks the segment, its blocks and its byte range, then calls the existing `SegmentDecoder.Decode`. A short or inconsistent layout returns `InvalidFrame` or `CorruptData`; `Write` returns `CapacityExceeded` for a short destination and leaves it untouched.

## Measured

Machine: AMD Ryzen 5 8500G, Windows 11 Pro, .NET SDK 10.0.401, runtime 10.0.12, Git Bash.

| Command | Result |
|---|---|
| `bash eng/dotnet_test.sh tests/SA.Animation.Tests/SA.Animation.Tests.csproj` | 208 of 208 passed on net10.0 and on netstandard2.1 (196 existing, 12 new) |
| `python eng/check_source_rules.py` | `source rules: ok` |
| The same 12 tests with `blocks.Slice((int)firstBlock, ...)` changed to `blocks.Slice(0, ...)` | 8 of 12 failed, so the tests detect a wrong block base. Change reverted |

What the 12 tests assert:

- Flat sampling returns the same bits as `SharedClip.Sample` (40-byte `Pose` compared as bytes) for 1, 2, 17, 18, 35 and 100 samples, packed and raw, looping and clamped, on every half-frame from 0.5 s before the clip to past its end plus 2,000 random times in -3 s to 3 s.
- The layout is contiguous, repeatable, and matches the loaded clip's blocks.
- 10 hand-written hostile `SegmentRange` values and 20,000 random corruptions of ranges, blocks and bytes return a defined `AnimationError` and never throw.
- 256 characters sampling one storage through `Parallel.For` produce the same bits as the serial loop.
- 1,000 warm calls allocate 0 bytes.

## Burst, measured in Unity

Unity 7000.0.0a16, Windows, Direct3D 12, project `D:\GitHub\_work\sa-probe`, bridge DLLs repacked from this branch with `python eng/pack_bridge.py`.

The first Burst compile of a job that calls `SegmentSampling.Sample` failed:

```
Burst error BC1025: Accessing the type `System.UInt16` (e.g. using `typeof`) is not supported
 at System.Runtime.InteropServices.MemoryMarshal.Read
 at System.Buffers.Binary.BinaryPrimitives.ReadUInt16LittleEndian
 at SA.Animation.PackedPosition.Decode
```

`BinaryPrimitives.Read*LittleEndian` goes through `MemoryMarshal.Read<T>`, which Burst cannot compile. The decode path in `src/SA.Animation/Streaming/PackedTracks.cs` now reads little-endian values with byte arithmetic (`Wire.Unsigned16`, and `Wire.Single` through an `int` reinterpreted as `float`). Only the reads used by `SegmentDecoder.Decode` changed; `Bind`, the encoders and `Wire.Double` still use `BinaryPrimitives` and are not Burst-safe.

After that change:

| Check | Result |
|---|---|
| `bash eng/dotnet_test.sh tests/SA.Animation.Tests/SA.Animation.Tests.csproj` | 208 of 208 on both builds, so the readers return the same values |
| Unity compile | 0 `error CS`, 0 `error BC` |
| `SharedFamilySystem` as a Burst job (com.sa.unity `packet/C17-shared-family-job`) | runs as Burst code, proven by a `BurstDiscard` probe |
| Trace recorded from the 0.3.7 main-thread system, 36 steps on a 7-bone and a 56-bone rig | 20,700 of 20,700 values equal bit for bit |
| EditMode, every SA assembly | 330 total, 299 passed, 0 failed, 31 skipped |
| 1000 rigs of 56 bones, median of 120 frames, Ryzen 5 8500G, 11 workers | 22.50 ms per frame before, 2.82 ms after |

`ReadOnlySpan<T>.Overlaps`, `stackalloc` spans and `ref readonly` locals compile under Burst as they are.
