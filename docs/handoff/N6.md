# N6 handoff: idempotent transition request

## What was built
`src/SA.Motion/Inertialization/TransitionRequest.cs`: `RequestState` (`Key`, `Membership`, `Revision`, `Active`),
`RequestDecision` (`Start`, `Keep`, `Misuse`), and `TransitionRequests.Decide` with the exact packet signature.
Decision order: inactive (`Active == 0`) starts fresh at revision 1; different key starts with the new key and
membership at the bumped revision; same key with different membership is `Misuse` with the state untouched;
same key and membership restarts only when `restart` is true and otherwise `Keeps` the state untouched.
Revision bumps with `revision == uint.MaxValue ? 1 : revision + 1`, so it wraps to 1 and is never 0.
Every input combination returns a decision; `default(RequestState)` is the inactive state.

`tests/SA.Motion.Tests/TransitionRequestTests.cs`: one test per rule, wrap from `MaxValue` to 1,
`MaxValue - 1` incrementing to `MaxValue`, a 20000-step fixed-seed (`1234567`) sequence compared field by
field against an independent reference implementation written in the test, a 5000-step revision-never-zero
sweep, a 5000-step never-inactive-after-start sweep, `Keep` applied twice, and `Misuse` applied twice.

Ambiguity note: `Misuse` takes precedence over `restart` (same key, different membership, restart true is
still `Misuse` with state untouched). Nonzero `Active` values other than 1 count as active; only `Active == 0`
is inactive. `restart` with a different key is an ordinary key-change `Start`.
