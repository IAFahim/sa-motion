## The format as built

`Write(LegParams.Standard)` gives 26 lines, one per `LegParam` in enum order,
each ended by a single `\n`, with no header and no trailing blank line:

```
Weight = 1
WeightHalfLife = 0.12
PlantHeight = 0.035
ReleaseHeight = 0.09
...
PelvisHalfLife = 0.08
```

Values use `float.ToString("R", CultureInfo.InvariantCulture)`.

`Read` starts from `fallback` and goes line by line:

- A line ends at `\n`, `\r\n` or a lone `\r`. Line numbers start at 1 and blank
  lines count. The last line needs no ending.
- The line, the name and the value are trimmed, so `Weight=0.5` and
  `<tab>Weight<tab>=<tab>0.5` read. Blank lines are skipped.
- The text is split at the first `=`. The name must equal
  `LegParamsSpec.Text(field).Name` exactly (case-sensitive).
- The value goes through `float.TryParse(..., NumberStyles.Float,
  CultureInfo.InvariantCulture, ...)`, must be finite, and must lie inside the
  inclusive `LegParamsSpec.Bounds` of its field. Then it is stored through
  `LegParamsSpec.With`.
- Every rejected line adds exactly one message `line N: reason` and leaves the
  previous value. Messages seen in a run:

```
line 1: unknown name 'Bogus'
line 1: expected Name = value
line 2: duplicate of an earlier Weight line
line 1: Weight is not a number: 'abc'
line 1: Weight is not finite: 'NaN'
line 1: MaxStretch is outside 1 to 1.25: '2'
text is null
```

## What the tests pin

- Round trip bit for bit (compared as integer bits, so `-0` and `+0` differ):
  every preset, 100 seeded random in-range profiles, all fields at their
  minimum, all at their maximum, and negative zero. Half of the random values are
  scaled toward the minimum; measured on those 100 profiles, 819 of the 2600
  written values use exponent text (the first is `ReleaseHeight = 2.5344732E-06`).
- The fallback used for those round trips is NaN in every field, so any field
  that is not actually read from the text fails the comparison.
- Format: a golden text for a known profile, shortest text (`0.1`, not
  `0.100000001`), and the same output under a current culture that uses a comma
  as decimal separator. Text with a decimal comma is rejected under that culture.
- Each of unknown name, malformed line, unreadable number, non-finite value,
  out-of-range value and duplicate gives exactly one problem that starts with
  the right line number, names the reason, and keeps the previous value. The
  unreadable, non-finite and out-of-range cases run for every one of the 26
  fields, and out-of-range includes one float step either side of each bound.
  Null text gives exactly one problem (`text is null`) and returns the fallback.
- Reversed and shuffled lines, CRLF, lone CR, mixed endings, a missing final
  line ending (including a one-character final line), odd spacing, blank lines.
- A generated-text test: 500 random texts built from lines whose outcome the
  generator already knows. The result and the list of rejected line numbers must
  match the generator's prediction exactly.
- A 3000-case sweep of garbage text (NUL, lone surrogate, byte-order mark,
  `U+2028`, huge exponents): never throws, every field stays finite and in
  range, at most one problem per non-blank line, and the same result with a null
  or an empty problems list.

## Mutation check (not part of the repo)

I applied 29 deliberate defects to `LegProfileText.cs`, one at a time, with a
throwaway script that lives in the session scratch folder and not in the repo.
Examples: current culture instead of invariant, `G9` instead of `R`, clamp
instead of reject, exclusive bounds, duplicates not detected, lone CR not a line
break, blank lines not numbered, split at the last `=`, case-insensitive names,
finite check removed, null list not guarded, last line dropped. Each one made at
least one of the 86 cases fail. The final pass over all 29 ran against the
committed tests. The script builds each defect from the original text and puts
the original back at the end; it reported the file restored byte for byte, and
`git diff HEAD` was empty and `git status` clean afterwards.
The first pass left one survivor (a one-character last line without a line
ending); `FinalLineWithoutALineEndingIsStillChecked` was added for it.

## Judgment calls the packet left open

1. **Duplicates.** A second line naming a field that an earlier line already set
   is a duplicate: one problem, and the earlier value stands, whatever the second
   line says. So `Weight = 0.25` then `Weight = 0.75` reads 0.25, not the
   fallback. A line whose value was rejected does not set the field, so a later
   valid line for that name still applies and is not a duplicate. Unknown names
   are never tracked: `Bogus` twice is two unknown-name problems.
2. **Read does not call `Sanitize`.** The packet asks for bit-for-bit round trips
   of any in-range profile, and independent in-range fields can break the
   ordering `Sanitize` enforces (`ReleaseHeight >= PlantHeight` and the other two
   pairs). Callers who need that ordering call `LegParamsSpec.Sanitize` after
   `Read`.
3. **Rejected means rejected.** Out-of-range values are reported, never clamped.
   Bounds are inclusive.
4. **Shape errors.** No `=`, or an empty name, is a malformed line. An empty value
   (`Weight =`) is reported as not a number. Both are one problem.
5. **Signature.** The parameters are annotated `string?` and `List<string>?`
   because null is handled. The runtime types are the ones in the packet. A null
   list means problems are not recorded; good lines still apply.
6. **Lone `\r` ends a line.** The packet only required CRLF; this costs nothing
   and avoids one confusing bad-number message for old-style endings.
7. **`Write` is total.** It writes whatever is in the struct, including NaN and
   infinities. Reading that text back reports one non-finite problem per field,
   which a test pins.
8. **Message wording is mine.** The packet fixed only "line number and reason".
   Tests pin the line prefix and the reason words, so changing the wording means
   updating `LegProfileTextTests.cs`.
9. **Test source stays ASCII.** Non-ASCII test strings use eight-digit Unicode
   escapes. A raw U+2028 inside a C# string literal is a line break and breaks the
   compile.

## Not verified, not done

- Unity was never started; this is a pure `src/` packet.
- `float.ToString("R")` and `float.TryParse` on Unity's Mono or IL2CPP: not
  measured. The netstandard2.1 library build was exercised only on the .NET 10
  runtime, because the test project targets net10.0. A runtime with an older
  float formatter is not covered.
- Windows and macOS: not run. The tests write their CRLF and CR text explicitly
  and do not depend on the platform newline.
- A leading byte-order mark is not stripped, and no test covers it because the
  packet does not ask for it. Probed with a scratch program: text that starts
  with U+FEFF reports `line 1: unknown name '<U+FEFF>Weight'` (one problem; the
  other lines still read). `File.ReadAllText` removes the mark (the first
  character was `W`), but `Encoding.UTF8.GetString` on the raw bytes keeps it.
- No docs outside this note were written, and no callers were added. The
  packet owns only the two files above.

## Open questions

- Is "first valid value wins, later lines for that name are duplicates" the rule
  the designers expect? The alternative, last value wins, would drop the
  duplicate problem and change one rule in `ApplyLine`.
- Should `Read` also report a profile that breaks the `Sanitize` ordering
  as a problem? It does not today (judgment call 2).
- Should `Read` skip a leading byte-order mark? A loader that decodes raw bytes
  with `Encoding.UTF8.GetString` would otherwise lose the first field. It is a
  one-line change; it was left out because the packet does not list it.
